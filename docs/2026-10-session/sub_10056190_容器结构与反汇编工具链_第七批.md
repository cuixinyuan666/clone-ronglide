## 二、方法论升级:自建反汇编工具链

### 2.1 为什么必须重建

前六批全部基于 `re-TAFLib.md`(IDA 风格文本报告,4 MB)。本批首次对该报告本身做**可靠性审计**,
结果发现两类问题:

| 问题 | 证据 | 影响 |
|---|---|---|
| **自动注释错误** | 报告称 `sub_10056190` "accesses memory-mapped peripheral registers at 0x66666667" | `0x66666667` 是**整数除法魔数**,与"外设寄存器"无关 —— 说明报告的自动分析部分**不可信** |
| **栈偏移记法漂移** | 见 §2.3 | 跨代码点用文本偏移比对栈槽会**得出错误结论** |

### 2.2 指令清单是准确的

对 `sub_1003d720`(迭代器 `++`)做**逐字节核对**,与报告完全一致:

```
报告:  0x1003d743: add dword ptr [esi+4],0A0h
实测:  0x1003d743: add dword ptr [esi + 4], 0xa0   ; 814604a0000000
```

**结论:报告的指令文本可用;不可用的是其自动注释与栈槽交叉引用。**

### 2.3 缺陷实证:`[esp+X]` 是当前-esp 相对

用自建栈跟踪(精确处理 `push`/`pop`/`sub esp`/`add esp`,并按被调函数 `ret N` 计算参数清理)
对 `sub_10056190` 全函数跟踪,得到**同一文本偏移对应不同帧偏移**的铁证:

| 报告文本 | 地址 | 该点 `esp` 相对入口 | **真实帧偏移** |
|---|---|---|---|
| `[esp+40h]` | `0x100561d1` | −1080 | **−1016** |
| `[esp+40h]` | `0x10056fd7` | −1040 | **−976** |
| `[esp+40h]` | `0x1005a15c` | −872 | **−808** |

**同一文本 `[esp+40h]`,在三处的真实变量互不相同。**

> **规则(此后必须遵守)**:源报告中的栈槽**只能在同一段连续代码内**用文本偏移比对;
> 跨代码点比对必须先用栈跟踪换算为帧相对偏移。

## 三、重大结构修正:容器是「内嵌 8 个 vector 的类 W」

### 3.1 发现过程

全 `.text` 扫描(142,887 条指令)找出**同时写 `+0x04/+0x08` 与 `+0x90/+0x94`** 的函数,命中
`sub_1003d910`(27 条指令,SEH 序言,`ret 4`)。其反汇编:

```asm
0x1003d910: push -1 / push 0x1006c91a / mov eax,fs:[0] ...   ; SEH 序言
0x1003d930: mov eax, dword ptr [esp + 0x14]   ; eax = this
0x1003d934: xor ecx, ecx                      ; ecx = 0
0x1003d936: mov dword ptr [eax + 0x04], ecx
0x1003d939: mov dword ptr [eax + 0x08], ecx
0x1003d93c: mov dword ptr [eax + 0x0c], ecx
0x1003d93f: mov dword ptr [eax + 0x14], ecx
0x1003d942: mov dword ptr [eax + 0x18], ecx
0x1003d945: mov dword ptr [eax + 0x1c], ecx
...   （以 16 字节为周期重复）
0x1003d975: fldz
0x1003d97d: mov dword ptr [eax + 0x7c], ecx
0x1003d980: mov dword ptr [eax + 0x94], ecx
...   0x98 0x9c 0xa0 0xa4 0xa8 0xac 0xb0 0xb4 0xb8
0x1003d9bc: fstp dword ptr [eax + 0x80]        ; +0x80 = 0.0f
0x1003d9c2: mov dword ptr [eax + 0x84], ecx
0x1003d9d7: ret 4
```

### 3.2 零化偏移揭示的 16 字节周期

被零化的偏移序列:

```
04,08,0C | 14,18,1C | 24,28,2C | 34,38,3C | 44,48,4C | 54,58,5C | 64,68,6C | 74,78,7C
```

**每 16 字节一组,每组零化前 3 个 dword,第 4 个 dword 不零化。**

对照 `sub_1003d9e0`(析构函数)释放的成员:

```asm
0x1003da39: mov eax,[esi+0x74]  → push eax → call 0x1006b320   ; operator delete
0x1003da57: mov eax,[esi+0x64]  → ... 释放
0x1003da75: mov eax,[esi+0x54]  → ... 释放
```

**释放的正是 +0x74 / +0x64 / +0x54 …… 即各 16 字节组的起始。**

### 3.3 修正后的结构模型

```c
/* 容器类 W —— 「分析上下文」，含 8 个内嵌 vector 成员
 * 每个成员占 16 字节：{ 头字段, _Myfirst, _Mylast, _Myend }
 * 构造函数零化 3 个指针；头字段(+0x00/+0x10/.../+0x70)由他处设置 */
typedef struct VectorMember {      /* 16 字节 */
    uint32_t   hdr;                /* 记录起始，构造器不零化 */
    void*      _Myfirst;           /* 记录 +0x04 */
    void*      _Mylast;            /* 记录 +0x08 */
    void*      _Myend;             /* 记录 +0x0C */
} VectorMember;

typedef struct AnalyzerCtx {       /* W，尺寸 ≥ 0xBC */
    VectorMember m[8];             /* +0x00, +0x10, +0x20, +0x30, +0x40, +0x50, +0x60, +0x70 */
    float        f_0x80;           /* +0x80 = 0.0f */
    uint32_t     u_0x84;           /* +0x84 */
    /* +0x88 / +0x8C / +0x90 不在构造器零化列表 → 由他处设置（分型/信号/状态） */
    uint32_t     u_0x94;           /* +0x94 */
    uint32_t     u_0x98 ... u_0xB8;
} AnalyzerCtx;
```

### 3.4 与引擎的对应关系

`sub_10056190` 函数头:

```asm
0x10056197: mov ebx,[esp+430h]     ; ebx = 参数 W
0x10056237: mov eax,[ebx+44h]      ; ★ W->m[4]._Myfirst
0x10056265: mov ecx,[ebx+48h]      ; ★ W->m[4]._Mylast
0x1005626a: mov eax,66666667h
0x10056271: sar edx,4              ; ÷160 → 元素个数
```

而在调用 `sub_1003f0d0` 时:

```asm
0x1005a1d4: mov ebx,[esp+43Ch]     ; ebx = W + 0x40（即 &W->m[4]）
0x1005a1e3: call 1003F0D0h         ; sub_1003f0d0 读 [ebx+4]=_Myfirst、[ebx+8]=_Mylast
```

**自洽**:`sub_1003f0d0` 用 `[ebx+4]`/`[ebx+8]` 取 `_Myfirst`/`_Mylast`,故 `ebx = 记录地址 − 4 = W+0x40`。
且 `sub_10056190` 自身用 `[ebx+44h]`/`[ebx+48h]`(ebx=W)取同一成员 —— **两条路径指向同一 vector**。

> **即:引擎遍历的是 W 的第 5 个内嵌 vector(`W->m[4]`,数据指针在 +0x44/+0x48),其元素为 0xA0 字节的「级别对象」。**

### 3.5 与 `sizeof(LevelObj)=0xA0` 无矛盾

前批曾出现"构造器写到 +0xB8 但步长只有 0xA0"的表面矛盾。**现已消解**:
`sub_1003d910` 构造的是**容器类 W(≥0xBC)**,不是 0xA0 的元素。二者是**不同层次的对象**。

## 五、`+0x94`(价格)写入者穷举

全 `.text` 扫描,**仅 4 个函数**写偏移 `+0x94`:

| 函数 | 形式 | 说明 |
|---|---|---|
| `sub_10001cc0` | `mov dword [esi+0x94], ebx` ×2 | 清零(疑似 W 的另一构造路径) |
| `sub_1003d910` | `mov dword [eax+0x94], ecx` | W 构造器清零 |
| **`sub_10056190`** | `fstp dword [..+0x94]` ×**24** | 主引擎:24 处价格写入(4 组 × 6) |
| **`sub_10060c00`** | `fstp dword [eax+0x94]` ×2 | **同族引擎**(见 §6) |

**关键**:**没有任何函数以「索引」形式写 0xA0 元素的 `+0x04`/`+0x08`。**
它们要么由批量拷贝(`rep movsd`)带入,要么其赋值路径尚未定位。

## 六、新发现:`sub_10060c00` —— 第 5 个同族引擎

`sub_10060c00`(被 `sub_10039e10` 调用)内部含**与 `sub_10056190` 完全同构**的片段:

```asm
0x100611aa: mov dword ptr [eax + 0x90], 4      ; ★ 状态 = 4（卖出组起点）
0x100611b4: cmp ecx, dword ptr [edx + 8]       ; 受检迭代器边界
0x100611d6: fld dword ptr [edx + 0xc]          ; ★ 读 LOW (+0x0C)
0x100611dd: fstp dword ptr [eax + 0x94]        ; ★ 写价格
...
0x10061699: fld dword ptr [edx + 0x10]         ; ★ 读 HIGH (+0x10)
0x100616a0: fstp dword ptr [eax + 0x94]        ; ★ 写价格
```

**意义**:印证第五批"同一算法在多个入口被内联复制"的判断 —— 除 `sub_10056190` 内部的 4 组之外,
**至少还有一个独立的同族引擎 `sub_10060c00`**。这解释了为何 `+0x90`/`+0x94` 的写入点分散在多个函数。

其栈槽模式 `[esp+0x28]`(=`_Mycont`)、`[esp+0x2c]`(=`_Myptr` 目标)、`[esp+0x5c]`(源元素)
与 `sub_10056190` 的 `[esp+40h]/[esp+44h]` **结构同构**,是受检迭代器三元组的又一次出现。

## 七、`+0x04`/`+0x08` 基数问题:状态与下一步

### 7.1 现状

- `+0x00`(序号)确为 **1 基**(输出时 `sub esi,1`,且空位补零 ⇒ 是稀疏的 K 线序号)。
- `sub_1003f0d0(vec, out, n)` = `vec.begin() + n`,**`n` 原样使用,无 ±1**。
- `n` 的来源是**元素对象的 `+0x04`(卖出组)/`+0x08`(买入组)**。
- **但这些字段的写入者未找到**(§5 已穷举 `+0x94`;`+0x04`/`+0x08` 在 0xA0 元素上无字段级写入)。

### 7.2 三种候选解释(按可能性排序)

| 假设 | 含义 | 佐证 | 反证 |
|---|---|---|---|
| **A. 容器含哨兵元素** | `m[4]` 的 `[0]` 是哨兵,真实元素 `i` 的序号为 `i`,故 `begin()+idx` 正确 | `sub_1003e200` 的循环从 `begin()+1` 起(`push 1; call 1003f0d0`),恰好跳过 [0] | 未观察到哨兵的构造代码 |
| **B. `+0x04`/`+0x08` 为 0 基位置** | 与 `+0x00` 不同基数(不同来源) | 无需哨兵 | 同一结构体内混用两种基数不合常理 |
| **C. 越界被断言掩盖** | 1 基导致末元素 `begin()+N == _Mylast`,被 `_invalid_parameter_noinfo` 静默吞掉 | 代码在写入前确有 `cmp _Myptr,_Mylast; jb` 断言 | Release 下断言无效,程序仍"正常工作"无法解释 |

### 7.3 下一步(第 8 轮建议)

工具链已就绪,**静态可做**的路径:

1. **找到 0xA0 元素的构造器**:扫描全 `.text` 中**以浮点写 `+0x94`** 且**同时写 `+0x04`/`+0x08`** 的函数(§5 已锁定范围),逐个展开其调用者,回溯 `+0x04`/`+0x08` 的实参来源。
2. **对 `sub_1003F170`(11,169 条指令)做递归下降反汇编** —— 前批用线性扫描未发现 `+0x04`/`+0x08` 写入,可能是**指令边界错位**导致漏检。用 capstone 递归下降重扫。
3. **数据流回溯**:从 `sub_10056190` 的 `push eax`(n 的来源)反向追踪 `[eax+8]` 的赋值链。
4. **动态验证**(需本机操作):x64dbg 断点 `0x1005a1fa`,读取 `[esp+44h]`(真实 `_Myptr`)、`[eax+8]`,与 K 线图标注比对。
