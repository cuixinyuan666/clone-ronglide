# WorkBuddy「自定义模型-测试连接」复查报告（2026-10-17）

> 用户反馈：最近录入的自定义模型在 WorkBuddy「设置-模型-自定义模型-测试连接」大部分不通过；但用户自己在 WorkBuddy 之外实测正常。
> 结论：**模型本身没有问题；失败是 WorkBuddy 内置测试的探测方式（stream:true + max_tokens:1）与 free 聚合网关（freellmapi）免费上游的波动叠加造成的"假阴性"。**

## 一、内置测试的真实实现（从 WorkBuddy 应用解包源码核实）

来源：`_asar_extract/main/server.js` → `async function testLocalCustomModelConnectivity(e,n)`。

| 项目 | 实测值 |
| --- | --- |
| 请求 | `POST {url}/chat/completions`（url 未以 /chat/completions 结尾则自动补齐） |
| body | `{"model": <id>, "stream": true, "max_tokens": 1, "messages": [{"role":"user","content":"Reply with OK."}]}` |
| 超时 | **30s**（AbortController） |
| 判定 | 401/403=UNAUTHORIZED；404=NOT_FOUND；429=RATE_LIMITED；其它非 200=REQUEST_REJECTED；200 时读 SSE 首个可解析 `data:` JSON（无 error 字段）=success，否则 INVALID_RESPONSE |

关键点：**探测用的是 `stream:true` + `max_tokens:1` 的极小流式请求**。

- `max_tokens=1, 非流式` → ✅ 200（返回 "The"）

⇒ 两个独立因素：(a) **流式路线当前健康状况**（同一模型流式/非流式路由不同上游尝试，流式尝试易返回空完成）；(b) **max_tokens 过小**在部分上游会放大"空完成"概率。

## 三、机制解释（为什么"内置测试红、自己测绿"）

1. freellmapi 把每个模型路由到多个免费上游"尝试"（attempt）；任一请求会在这些尝试间轮询重试。
2. **流式 + 极小 max_tokens** 的请求形态命中"空完成（empty_completion）"的概率显著偏高；全部尝试都空 → 网关返回 502 → 内置测试判 REQUEST_REJECTED。
3. 免费上游还有**分桶限流（429）**，时点性更强（如 05:40 前后 glm/qwen3-next 全线冷却，而 20 分钟后恢复）。
4. 用户自己测试（非 WorkBuddy）通常是非流式 / 正常 max_tokens / 不同时点 → 通过。
5. **真实使用不受影响**：本轮 rev 评审中 nemotron 以流式跑了 11 分钟完成任务、devstral/mistral-small/sensenova 流式均正常——即这些模型在 WorkBuddy 内实际可用。

## 四、建议

1. **把内置测试结果仅当参考**：红了先看我的复现脚本的 control 列；control 绿 = 模型可用。
2. **（可选，需用户确认后实施）搭一个 5 分钟小改造**：本地 compat shim（如 `127.0.0.1:31499`）把 `max_tokens=1` 改写为 32 再转发给 freellmapi；把自定义模型的 URL 改为 shim 地址，内置测试即可对"流式路线健康"的模型转绿。注意：对流式路线本身波动的模型（如当前时点的 nemotron），shim 也无法保证 100% 绿——这是上游波动，不是配置问题。
3. **日常检查通道**：`wb_testconn_repro.py <model...>`（WBtest + control 双列）；评审流水线的 `preflight_t.py`（带 tools、max_tokens=8）则用于确认"子代理工具调用"可用性。
4. 修正我们自己的预检习惯：**预检 max_tokens 不要用 1**（会用 empty_completion 误伤模型）；本轮已将相关脚本默认值调至 ≥8，并记录"预检后不宜立刻 spawn（会吃掉路线配额窗口）"的经验。
